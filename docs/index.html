Which alerts get escalated?

A financial-monitoring unit reviews automated alerts built from customers' transaction history. Specialists escalate about one in six (17.2 %) and dismiss the rest. We estimate the escalation probability of 6,000 hidden alerts from the 180 days of transactions behind each one.

Approach

One alert, one row: summarise the history, then let cross-validation decide

The transaction table is relational: 6,987,663 training transactions belong to 14,000 alerts, and the target lives on the alert. We therefore summarise each alert's own history into one row of features and model at the alert level. No statistic is ever computed on the test set, and every fitted quantity (thresholds, normalisation, feature selection, calibration) is fitted inside the training folds.

Ideas were borrowed from past Kaggle competitions with the same structure (Home Credit, AmEx, Elo, IEEE-CIS). Each was first tested on this data; in total 123 experiments were run, each accepted or rejected by the same rule.

  1. Explore the history behind each alert and record every finding as a measured fact or a labelled assumption.
  2. Aggregate each alert's transactions into ~470 candidate features in 16 families, plus scores from a transaction-level model.
  3. Judge every family with repeated stratified 5-fold cross-validation (3 fixed repeats) and one acceptance rule: keep a change only if the mean AUC rises by at least 0.0010 and it rises in all three repeats.
  4. Tune, add models to a rank-average ensemble under the same rule, calibrate on training predictions, and predict the hidden alerts.

From findings to features

Most ideas did not survive the acceptance rule — the ones that did: F1 · Amount statistics, F7 · Contrasts, fi · Cell interactions, exp-aggregates

Every family was added to the current best set one at a time and scored on the same 3 × 5 folds; Δ is the change in out-of-fold ROC-AUC in each repeat. Round 1 compared most families against F1+F2 and round 2 re-tested the rejected ones against F1+F2+F7. Phase 3 added five new ideas (kNN target mean, class density ratio, histograms, rank transforms, cell interactions); once the interactions were accepted, every family rejected so far was re-tested against the new base, and leave-one-out on the final set removed F2. Hyper-parameter tuning (three variants), seed averaging and monotone constraints did not pass the rule, so every row uses the same LightGBM settings.

Measured, not assumed: scored on its own, F1 reaches 0.6446, practically the whole baseline. Several rejected families carry signal by themselves (Threshold shares 0.621, exp-aggregates 0.618, Time windows 0.611, Burst 0.562) yet add less than the threshold on top of F1, so their information overlaps with the amount statistics. The cell-interaction gain comes from the differences between cell levels: removing them changes AUC by -0.0045, removing the products by +0.0005. Null-importance feature selection was tested and rejected.

Validation & models

From 0.6443 to 0.6528 cross-validated ROC-AUC

Why a random stratified split. Train and test alerts are interleaved over the same months and the escalation rate is stable, so a random split reproduces the test situation. A time split (as in Kaggle IEEE-CIS, where test lies after train) would answer a different question.

Why no group split. No transaction is shared between alerts and there is no customer key, so there is nothing to group by. Each alert's transactions stay inside its fold because the model sees one row per alert.

Acceptance rule. Model-seed noise alone moves AUC by up to 0.0008 per repeat, so a change is kept only if the mean over three repeats improves by at least 0.0010 and every repeat improves. The rule was fixed before modelling and applied to every experiment, including ensemble members.

Repeated stratified 5-fold, 3 repeats

Blue: validation fold. Every fitted statistic (thresholds, normalisation, PCA, feature selection, the model) sees only the other four folds. Hyper-parameters, the feature-selection threshold and the spline penalty were chosen on separate tuning repeats (seeds 100 and 101), never on the three scoring repeats.

Conclusions

What we learned

Amount level is the signal. Escalated alerts move smaller amounts, most clearly in bank transfers (density ratio about 1.15 in the smallest band, 0.72 in the largest). Per-type amount levels are correlated (0.75–0.87), and F1 alone reproduces the baseline score.

Relative levels matter. The largest single gain (+0.0046) came from differences between the amount levels of an alert's own cells, such as outgoing versus incoming bank transfers or each cell versus the alert's overall level. Trees can in principle build such differences, but here giving them explicitly paid off in all three repeats.

Volume and timing add little. Escalated alerts are 4–9 % more active over the whole window; the volume family helped at first (+0.0012) but became redundant once the interaction features were in (removing it then gained +0.0011). The burst family gained only +0.0006, time of day shows no difference between the classes, and date features were rejected.

Weak features, careful validation. No single aggregate we scored exceeds AUC 0.574; three rounds of hyper-parameter tuning won on the tuning repeats but not on the scoring repeats. The final model reaches 0.6528 ± 0.0009 out-of-fold ROC-AUC.

Assumptions, not facts. That miqdor_indeksi is a z-scored log amount, that the floors and caps are clipping by the data generator, and that the burst is a generation artefact rather than the triggering activity are interpretations; the data cannot confirm them.

Synthetic data. The organisers generated and localised the data, so the patterns describe the generator, not real banking behaviour.

One submission. There is no leaderboard feedback; every decision rests on cross-validation, which is why the acceptance rule is strict.

Reproduce

Everything runs from the repository

The pipeline code and the reproducible notebook are in the repository. Put the four data files into data/, create the environment, then run the notebook: it rebuilds the features from the raw files, trains the final model on the fixed folds, checks the scores against the reference values and writes the submission file (about a minute on a laptop CPU).

python -m venv .venv && .venv/Scripts/pip install -r requirements.txt
jupyter nbconvert --to notebook --execute notebooks/FB203632_pipeline.ipynb --output FB203632_pipeline.ipynb
